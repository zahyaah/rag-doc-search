# ADR-0004: Evaluation methodology and sample sizes

## Status
Accepted

## Date
2026-09-22

## Context
The assignment requires: "For each document in the test set, generate a
query that ideally returns that document as a relevant result," then
measure retrieval accuracy, plus automated (ROUGE) and human evaluation of
summary quality. The binding constraint is OpenRouter's free-tier cap of
50 requests/day (see `docs/decisions/0003-llm-provider.md`), which the
eval loop itself consumes via LLM calls for both query generation and
summarization.

## Decision
- **Test set:** 15 documents, sampled (seeded) as a *subset of the
  500-document corpus* (not held out) — so retrieval can actually
  succeed; a held-out doc would never be found by definition.
- **Retrieval eval:** for each of the 15 test docs, one LLM call generates
  a natural-language query (5-12 words) that the article should answer.
  That query is run through `HybridSearcher`, and we check whether the
  source doc appears in the top-K for K ∈ {1, 3, 5, 10}, reporting
  Recall@K and Mean Reciprocal Rank (MRR).
- **Summarization eval:** for 8 of those 15 test docs (further capped to
  conserve request budget), the article is summarized (medium length,
  ~120 words) and scored against CNN/DailyMail's `highlights` field with
  ROUGE-1/2/L (`rouge_score`, `use_stemmer=True`), reporting F1.
- **Human evaluation:** not crowdsourced — a scoring worksheet
  (`data/human_eval_worksheet.md`, Coherence/Coverage/Accuracy 1-5 per
  doc) was generated for the 8 summarized documents for the assignment
  author to rate directly, rather than substituted with agent
  self-review (see Consequences).
- Generated queries are cached to `data/eval_queries.jsonl` so a re-run of
  `rag/evaluate.py` doesn't re-spend the query-generation budget.

Budget: 15 (query-gen) + 8 (summarize) = 23 calls per full eval run,
leaving headroom under the 50/day cap for live debugging and the
Streamlit demo in the same session.

## Alternatives Considered

### Larger test set (e.g. 100+ docs)
- Pros: tighter confidence intervals on Recall@K / ROUGE.
- Cons: would alone consume 200+ LLM calls (query-gen + summarize),
  blowing the daily free-tier budget before any live demo/debugging
  could happen.
- Rejected for this deadline; sample size is a documented limitation,
  not an oversight.

### Held-out test set (docs excluded from the indexed corpus)
- Pros: closer to a "can it generalize" evaluation.
- Cons: contradicts the assignment's literal instruction ("create a
  subset of the corpus as a test set" — a subset is *in* the corpus by
  definition), and retrieval would trivially fail 100% of the time since
  the target document isn't indexed.
- Rejected as a misreading of the spec.

### Crowdsourced/multi-rater human evaluation
- Pros: what the assignment literally asks for.
- Cons: not feasible to recruit and run raters same-night.
- Rejected for time; substituted with documented manual spot-checks.

## Consequences
- Retrieval metrics are optimistic relative to real user queries: the
  eval queries are generated by an LLM *reading the target article*, so
  they tend to reuse the article's own vocabulary — closer to a
  best-case query than a naive user's. Recall@1 = 0.93, Recall@{3,5,10}
  = 1.0, MRR = 0.97 on the 500-doc corpus (see `data/eval_results.json`)
  should be read in that light, not as a claim that any real-world query
  phrasing will do this well.
- ROUGE F1 (rouge1 ≈ 0.20, rouge2 ≈ 0.07, rougeL ≈ 0.13) is depressed by
  a stylistic mismatch, not necessarily poor summarization: our
  summarizer produces fluent paragraphs, while CNN/DailyMail
  `highlights` are terse, telegraphic bullet fragments. An example pair
  is included in `REPORT.md` to make this concrete rather than leaving
  the number unexplained.
- Until the human-eval worksheet is returned filled in, summarization
  quality claims in `REPORT.md` rely only on ROUGE plus an explicitly
  labeled agent self-review — qualified accordingly, not presented as
  independently verified (see `REPORT.md` §4.4 for status).

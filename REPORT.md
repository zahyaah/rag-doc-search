# Document Search and Summarization Using LLMs — Report

## 1. Objective

Build a system that searches a corpus of news articles and returns
relevant documents for a free-text query, then summarizes the retrieved
documents with an LLM to a user-specified length, and evaluate both the
search and summarization steps. This report covers data preparation,
methodology, evaluation results, and challenges encountered. See
`README.md` for setup/run instructions and `docs/decisions/` for the
detailed rationale (ADRs) behind each architectural choice referenced
below.

## 2. Data Preparation

**Corpus:** CNN/DailyMail (`abisee/cnn_dailymail`, config `3.0.0`), pulled
via HuggingFace `datasets`. 500 articles from the `test` split form the
searchable corpus; a random, seeded 15-article subset of that same corpus
is held aside as the evaluation test set (a *subset*, not held-out, per
the assignment's phrasing — see `docs/decisions/0002-corpus-choice.md`).

This dataset was chosen specifically because each article ships a
human-written reference summary (`highlights`), which makes ROUGE
evaluation possible without a separate labeling effort under a same-day
deadline.

**Cleaning (`rag/data_prep.py`):**
- Strip the `(CNN) --` / `(CNN)` wire-service byline prefix via regex.
- Strip a `By . <author> . PUBLISHED: ... UPDATED: ...` byline block
  present in some DailyMail-sourced rows.
- Collapse all whitespace/newlines to single spaces.
- Drop any article under 40 words (malformed/near-empty rows).

Each cleaned record stores `doc_id` (source dataset id), `title` (first
sentence, truncated to 120 chars, used for display/auto-suggest), `text`
(cleaned article body), and `reference_summary` (the original
`highlights`, used only for evaluation, never shown to the retriever).

**Reproducibility:** `random.seed(42)` fixes which 15 docs become the test
subset across re-runs.

## 3. Methodology

### 3.1 Document Search (`rag/search.py`, `rag/indexing.py`)

Hybrid retrieval combining:
- **BM25** (`rank_bm25.BM25Okapi`) over whitespace-lowercased tokens —
  lexical/keyword matching.
- **Dense embeddings**: `sentence-transformers/all-MiniLM-L6-v2`
  (384-dim), indexed with FAISS `IndexFlatIP` on L2-normalized vectors
  (inner product = cosine similarity after normalization) — semantic
  matching.

Both score vectors are min-max normalized to `[0, 1]` per query, then
combined as a weighted sum (default 0.5 BM25 / 0.5 embedding, both
configurable in `rag/config.py`). The top N documents by combined score
are returned with per-signal score breakdowns, so a user can see whether
a result matched on keywords, meaning, or both.

Full rationale and alternatives considered: `docs/decisions/0001-hybrid-retrieval.md`.

### 3.2 Document Summarization (`rag/summarize.py`, `rag/llm_client.py`)

Retrieved documents are concatenated (with document boundaries marked)
and sent to an LLM with a target word count derived from a user-selected
length (`short`=50, `medium`=120, `long`=250 words, or an explicit
integer). The LLM is instructed to produce one coherent summary spanning
all input documents, without inventing information not present in them.

LLM calls go through OpenRouter's OpenAI-compatible API, using
`nvidia/nemotron-3-super-120b-a12b:free` with reasoning explicitly
disabled (see `docs/decisions/0003-llm-provider.md` for why and the
concrete bug this avoided). Retries with exponential backoff handle rate
limiting (429) and upstream provider errors (502/503, including the case
where OpenRouter returns HTTP 200 with an `error` body instead of
`choices` — see Challenges below).

### 3.3 Evaluation (`rag/evaluate.py`)

Two eval passes, both bounded by OpenRouter's free-tier cap of
50 requests/day (20/minute) — see `docs/decisions/0004-evaluation-methodology.md`
for the full reasoning behind the sample sizes below.

**Retrieval accuracy:** for each of the 15 test-set documents, an LLM
reads the article and generates a natural-language query (5-12 words) it
should answer. That query is run through the hybrid searcher, and we
record whether/where the source document appears in the ranked results,
reporting Recall@{1,3,5,10} and Mean Reciprocal Rank (MRR).

**Summary quality:** for 8 of the 15 test documents, the article is
summarized (medium length) and compared against its CNN/DailyMail
`highlights` using ROUGE-1/2/L F1 (`rouge_score`, `use_stemmer=True`).

**Human evaluation:** a scoring worksheet (`data/human_eval_worksheet.md`)
was generated for the 8 summarized documents (Coherence/Coverage/Accuracy,
1-5) for the assignment author to rate directly, rather than a
crowdsourced pass — see §4.4 for status and results once returned.

## 4. Evaluation Results

Full machine-readable results: `data/eval_results.json` (generated by
`uv run python -m rag.evaluate`).

### 4.1 Retrieval accuracy (15 queries, 500-doc corpus)

| Metric | Value |
|---|---|
| Recall@1 | 0.933 |
| Recall@3 | 1.000 |
| Recall@5 | 1.000 |
| Recall@10 | 1.000 |
| MRR | 0.967 |

Sample generated queries (all retrieved the source doc at rank 1):
- "UN official says cargo ship may have capsized migrant boat in Mediterranean"
- "FBI confirms Marwan killed in Philippines raid, removes from most wanted terrorists list"
- "Anne Frank died earlier than thought new research typhus Bergen-Belsen 1945 date of death correction"

**Reading these numbers honestly:** queries were generated by an LLM
*reading the target article*, so they reuse the article's own
entities/vocabulary — this is closer to a best-case query than a typical
user's phrasing. The near-perfect scores demonstrate the retrieval
mechanism works correctly, not that any real-world query will do this
well. A harder, more realistic eval would generate queries from only a
document's *topic* (without full-text access) or use genuinely
independent user queries.

### 4.2 Summarization quality (8 documents, ROUGE F1)

| Metric | Average |
|---|---|
| ROUGE-1 | 0.199 |
| ROUGE-2 | 0.072 |
| ROUGE-L | 0.133 |

Per-document range: ROUGE-1 from 0.138 to 0.264; ROUGE-2 from 0.021 to
0.124; ROUGE-L from 0.072 to 0.179 — see `data/eval_results.json` for
all 8 rows.

These are noticeably lower than typical published CNN/DailyMail
abstractive-summarization baselines (ROUGE-1 commonly 0.35-0.40+). This
is investigated in §4.3, not treated as a bare number.

### 4.3 Why ROUGE is low here (and what it does/doesn't mean)

Example (doc 1, ROUGE-1 = 0.233, ROUGE-L = 0.143):

> **Generated:** "The migrant boat that sank in the Mediterranean over the
> weekend, resulting in one of the deadliest known disasters involving
> migrants crossing from North Africa, may have capsized due to a large
> wave created by the cargo ship King Jacob as it approached to assist,
> according to survivors interviewed..."
>
> **Reference (`highlights`):** "Shipping company representative denies
> cargo ship caused the capsizing . UNHCR spokeswoman tells CNN that a
> cargo ship may have touched the migrant boat . Italian authorities have
> arrested two survivors on suspicion of human trafficking ."

The generated summary is factually consistent with the article and
readable as prose. The reference is a very different *genre* of
text — three short, independently-extracted bullet fragments, each
naming a distinct sub-fact, written in CNN/DailyMail's telegraphic house
style. ROUGE is an n-gram overlap metric, so it penalizes our fluent
paragraph for not reproducing the reference's specific bullet phrasing,
even where the underlying facts agree.

### 4.4 Human evaluation

The assignment requires human evaluation of summary quality as a
complement to ROUGE. An LLM cannot perform this step authentically — a
model rating its own (or a sibling model's) output is not independent
human judgment, so this deliverable is a **process**, not a number the
agent could legitimately generate itself: a scoring worksheet
(`data/human_eval_worksheet.md`) covering all 8 summarized documents,
each entry showing the article excerpt, generated summary, reference

report's author to complete as the final step before submission.

## 5. Challenges Faced and Solutions

1. **OpenRouter free-tier daily cap (50 requests/day, <$10 credit).**
   Directly shaped the eval design: sample sizes capped at 15 (retrieval)
   + 8 (summarization) = 23 calls per run, with generated queries cached
   to `data/eval_queries.jsonl` so re-running the eval script doesn't
   re-spend budget on already-generated queries. See
   `docs/decisions/0004-evaluation-methodology.md`.

2. **Hidden reasoning tokens silently eating the response budget.**
   The chosen model (`nvidia/nemotron-3-super-120b-a12b:free`) reasons
   before answering by default; a 10-token budget for a one-word reply
   returned a truncated chain-of-thought fragment instead of the answer.
   Fixed by disabling reasoning via `"reasoning": {"effort": "none"}`
   (source: OpenRouter's reasoning-tokens docs). See
   `docs/decisions/0003-llm-provider.md`.

3. **OpenRouter returning HTTP 200 with an error body.** A live eval run
   crashed 11/15 calls into query generation with `KeyError: 'choices'`.
   Root cause: for upstream provider failures, OpenRouter can return a
   200 status with `{"error": {...}}` instead of `choices` — the HTTP
   status code alone doesn't indicate success. Fixed `rag/llm_client.py`
   to check the response body for an `error` field (and
   `finish_reason: "error"` inside a partial `choices` entry) and retry
   those the same as HTTP 429/502/503. Regression tests added
   (`tests/test_llm_client.py`) reproducing both failure shapes.

4. **CNN boilerplate-stripping regex missed a real case.** A unit test
   (`tests/test_data_prep.py::test_removes_cnn_prefix`) caught that the
   original regex `\(CNN\)\s*--?\s*` required a literal dash after
   `(CNN)`, so articles formatted as `(CNN)The mayor said...` (no dash)
   were left with the prefix intact. Fixed to
   `\(CNN\)\s*(?:--\s*)?` (dash now optional).

5. **Test-set semantics.** The assignment says "create a subset of the
   corpus as a test set" — initially implemented as a *held-out* split
   (docs excluded from the indexed corpus), which would make retrieval
   accuracy trivially 0% by construction (an unindexed doc can never be
   retrieved). Corrected to sample the test set *from within* the indexed
   corpus, matching the literal instruction. See
   `docs/decisions/0002-corpus-choice.md`.

## 6. Scalability and Efficiency Notes

- Both BM25 (`get_scores`) and FAISS `IndexFlatIP` are exact,
  brute-force search — O(n) per query. At 500 documents this is
  effectively instant; it would need to move to an approximate index
  (FAISS `IndexIVFFlat` or `IndexHNSWFlat`, and a proper inverted index
  for BM25, e.g. Elasticsearch/OpenSearch) once the corpus reaches
  roughly 100k-1M+ documents. See `docs/decisions/0001-hybrid-retrieval.md`
  Consequences.
- Embeddings are computed once at index-build time and cached to disk
  (`data/faiss.index`, `data/doc_store.pkl`, `data/bm25.pkl`); query-time
  cost is one embedding call + two O(n) scans, not re-embedding the
  corpus.
- The LLM is only invoked for summarization (on-demand, user-triggered)
  and for eval query generation — never in the hot path of a plain
  search. This keeps interactive search latency low regardless of LLM
  provider speed/availability.
